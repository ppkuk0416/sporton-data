# 06:30 보고서 지연 사고 점검

## 실제 기록

예약 실행 43140845366의 GitHub event는 schedule이다. 생성은 UTC 2026-11-12
02:21:35 = KST 11:21:35, 잡 시작 02:21:38, Telegram 성공 기록은 02:22:48.787777
= **KST 11:22:48**다. 예정 06:30보다 약 4시간 53분 늦게 전달됐다. 실행 시간은
약 1분이므로 주 지연은 수집·모델 실행 이전의 GitHub 예약 트리거 생성 단계였다.

실제 artifact DB의 메시지 ID 12와 `telegram_sent` 원본을 확인했다. 다음 예약
43143839901은 이미 보낸 기록을 복원해 `already_sent`로 종료했다. GitHub의 녹색
success를 정시 도착 성공으로 해석하면 안 된다.

사용자 요청 후 수동 복구 43316374354는 Telegram 메시지 ID 14, UTC
2026-11-12 22:05:40 = **KST 2026-11-13 07:05:40**에 발송 성공했다. 실제 날짜의
새 자료로 생성했으며 사전/사후 구분을 유지했다.

## 수정

- GitHub warm start를 UTC 16:00 = KST 다음날 01:00에 추가했다.
- 일찍 시작된 runner는 자체 시계로 06:30을 기다리고 그때 수집·분석을 시작한다.
  기존 06:30·06:40·06:50·07:00 복구 트리거도 유지한다.
- 대기는 5시간 45분 이하로 제한하고 잡 수명은 GitHub 상한인 360분으로 설정했다.
- 이미 늦게 시작했다면 다음날까지 기다리지 않고 현재 날짜의 복구를 진행한다.
- 기존 전송 영수증·직렬 실행을 유지해 재시도의 중복 보고서를 막는다.
- 실제 지연 실행을 발견하면 날짜당 한 번 지연 알림을 시도하고 상태/시각을 저장한다.
- mock 시계의 정시 대기·늦은 시작·수명 초과·하루 한 번 알림과 기존 회귀를 포함한
  관련 테스트 36개가 통과했다. 별도 DB의 실제 2초 타이머도 실행했다.

## 한계

이것은 관측된 약 5시간 트리거 지연을 흡수하는 완화책이다. GitHub가 warm start도
늦게 실행하거나 아예 실행하지 않으면 정시를 보장할 수 없다. 미래의 실제 06:30
실행을 지금 성공으로 기록하지 않는다. 엄격한 정시 SLA에는 상시 실행 호스트와
독립 외부 감시가 필요하다. 대기 중인 warm job은 같은 concurrency의 수동 작업을
지연시킬 수 있으며, 긴급 복구 시 실행 단계를 확인하고 처리해야 한다.
